# Narracode Literary Capacity Plan

Created: 2026-05-14 08:45 CEST
Created by: GPT-5.5 Codex
Purpose: conceptual implementation plan for improving Narracode's capacity to write full literary stories

## Scope

This plan examines the proposed Narracode function in `README.md` and `narracode.md`, while ignoring the historical computational narrative examples in the README. It treats Claude Code as an architectural inspiration: a disciplined agentic harness around a model, not merely a prompt style.

The focus is conceptual: what should Narracode become so it can support sustained literary storytelling across many sessions, drafts, revisions, and human interventions.

## Diagnosis Of Current Narracode

Narracode already has a strong core insight: literary generation improves when the model is forced to separate roles, externalize memory, and let critical recognition govern generative default.

Current strengths:

- Clear role separation: Initiator, Reading, Structural, Compositional, Reflexive, Expansion.
- External symbolic state: `POETICS.md`, `structural/graph.md`, `time-constants.md`, `history.md`.
- Hooks for structural sync, snapshotting, drift checks, edit learning, and orientation.
- Strong aesthetic principle: the harness should interrupt fluent median output.
- Good human-in-the-loop posture: the prompter remains authorial, and manual edits teach the system.

Current limits:

- The symbolic state is too thin for full literary fiction. It tracks history, relations, and time, but not enough of scene pressure, perceptual texture, motifs, unresolved promises, affective weather, narrative withholding, interior transformation, or reader memory.
- The Compositional Agent reads too much undifferentiated context and has no formal "context pack" optimized for the next scene.
- Revision is under-specified. Narracode can critique and continue, but it does not yet have a robust process for deep structural revision, line revision, compression, modulation, or re-ordering.
- The Reading Agent is mainly source/style oriented. It should also produce reusable craft constraints, not just annotations.
- The Reflexive Agent checks drift, but there is no multi-axis literary verification layer analogous to tests in code.
- The current harness is a single markdown protocol. It needs a command vocabulary, modular skills, state schemas, and deterministic hooks if it is to become a real Claude Code-like tool.

## Central Design Principle

Narracode should stop treating "the next draft" as the main unit of generation.

For full literary storytelling, the central unit should become the scene-cycle:

1. Orient the project.
2. Select or infer the next narrative obligation.
3. Assemble a compact context pack.
4. Draft one scene or sequence.
5. Run literary verification.
6. Capture what changed.
7. Update symbolic state.
8. Wait for human decision.

The draft is only one step inside a larger literary control loop.

## Proposed Architecture

### 1. Replace Thin Structural Memory With A Layered Story State

Keep the existing `structural/` folder, but expand it into distinct literary surfaces:

```text
structural/
  history.md              established events, facts, refusals
  graph.md                characters, entities, relation changes
  time-constants.md       chronology, durations, simultaneities
  obligations.md          promises, unanswered questions, planted objects, withheld knowledge
  motifs.md               recurring images, objects, phrases, gestures, symbolic pressures
  affect.md               emotional weather by scene, character, and location
  character-interiority.md private knowledge, shame, desire, contradiction, avoidance
  reader-state.md         what a first-time reader likely remembers, expects, misunderstands
  scene-ledger.md         scene list with function, pressure, turn, aftermath
```

Why this matters:

- Literary continuity is not only factual continuity.
- A long story often fails because the model forgets obligations, tonal pressures, or what the reader has been taught to care about.
- `reader-state.md` is especially important: code tests check behavior; literary tests should check the imagined reader's accumulated attention.

### 2. Add A Context-Pack Compiler

Claude Code works partly because it constantly manages context: project memory, files, current task, tools, and verification. Narracode needs the equivalent for scenes.

Before each draft, generate a temporary file:

```text
context/next-scene-pack.md
```

It should include only:

- current prose endpoint
- immediate prior scene summary
- active characters and their private states
- active obligations relevant to the next scene
- active motifs to continue, bend, or refuse
- time and location constraints
- reader-state summary
- POETICS rules relevant to this scene
- explicit current human request
- "do not include" constraints

This prevents the Compositional Agent from rereading the whole project as mush. It gives the model a sharp local field.

### 3. Introduce Literary Verification As Tests

Narracode should borrow the spirit of test suites, without reducing literature to scores.

Create a `checks/` layer:

```text
checks/
  continuity-check.md
  voice-check.md
  scene-function-check.md
  reader-state-check.md
  obligation-check.md
  line-pressure-check.md
  anti-mediocrity-check.md
```

Each check should produce findings, not grades.

Suggested checks:

- Continuity: contradicts any established event, time, relation, or known fact?
- Voice: does the prose slip toward generic LLM cadence, summary, sentimentality, or explanatory closure?
- Scene function: did the scene change anything, reveal anything, delay anything intentionally, or intensify an existing pressure?
- Reader state: what would a reader now expect or remember?
- Obligation: did the scene accidentally resolve, ignore, or introduce promises?
- Line pressure: are sentences doing perceptual, rhythmic, and dramatic work?
- Anti-mediocrity: which paragraphs are merely competent?

These checks should run after drafting, before structural update. The human can decide whether to revise.

### 4. Split The Compositional Agent Into Drafting Modes

The current Compositional Agent is too broad. Full storytelling requires different writing operations.

Recommended modes:

- `scene`: writes the next scene from a context pack.
- `bridge`: moves between scenes without pretending the transition is a full scene.
- `interior`: deepens a character's perception, memory, shame, desire, or contradiction.
- `object`: writes through a material object, place, or sensory system.
- `dialogue`: handles pressure through speech, silence, and misrecognition.
- `compression`: reduces a section without losing signal.
- `expansion`: thickens a thin section while preserving its purpose.
- `recast`: rewrites the same event through a different focalization or temporal posture.

This is the literary equivalent of Claude Code using specialized tools or subagents instead of one generic action.

### 5. Create True Revision Agents

Narracode currently critiques more clearly than it revises. Add dedicated revision roles:

- Structural Revision Agent: reorders, cuts, combines, or moves scenes.
- Line Revision Agent: revises prose at the paragraph and sentence level.
- Continuity Repair Agent: fixes contradictions with minimal aesthetic disturbance.
- Density Agent: increases specificity, materiality, relation, or interior pressure.
- Silence Agent: removes explanation, over-signaling, and forced closure.

Each revision agent should write to a new draft file or patch file, never overwrite silently.

### 6. Formalize Human Edit Learning

The Seamless Edit Method is one of Narracode's best ideas. Make it more exact.

Instead of only `edit-observations.md`, add:

```text
learning/
  edit-diffs/
  style-rules-candidates.md
  accepted-style-rules.md
  rejected-style-rules.md
```

The system should distinguish:

- local edit: applies only here
- recurring preference: candidate for POETICS
- hard rule: human explicitly accepts
- rejected inference: model misunderstood the edit

This avoids the danger of over-learning from one beautiful exception.

### 7. Add A Reader Simulation Pass

A long literary work depends on a reader carrying partial memory, expectation, confusion, and emotional charge.

Add a Reader Simulation Agent that answers:

- What does a first-time reader believe is happening?
- What are they waiting for?
- What have they forgotten?
- What feels intentionally mysterious versus accidentally unclear?
- What emotional or symbolic charge has accumulated?
- Where has attention slackened?

This should update `structural/reader-state.md`.

### 8. Treat POETICS As A Constitution, Not A Junk Drawer

`POETICS.md` should not absorb every observation. It should have stable sections:

```text
# POETICS

## Core Commitments
## Refusals
## Attentional Dialect
## Syntax And Rhythm
## Character Logic
## World Logic
## Image Systems
## Reader Contract
## Accepted Human Style Rules
## Temporary Experiments
```

Rules should have status:

- active
- experimental
- retired
- contradicted by human edit

This makes the aesthetic state inspectable.

### 9. Build A Command Surface

Claude Code's slash commands matter because they turn fuzzy intention into reliable workflows. Narracode should develop commands even if they begin as markdown conventions.

Suggested commands:

```text
/init-story
/orient
/scene
/bridge
/critique
/drift
/revise-lines
/revise-structure
/reader-sim
/snapshot
/learn-edits
/context-pack
/obligations
/motifs
/export
```

Each command should declare:

- role invoked
- files read
- files written
- whether it may modify drafts
- whether it stops afterward

The command layer is what turns Narracode from advice into an operable harness.

### 10. Add Hooks Around The Literary Loop

Borrow Claude Code's hook concept, but adapt it for writing.

Suggested hooks:

```text
pre_scene:
  update structural state
  compile context pack
  check unresolved obligations

post_scene:
  run literary checks
  update reader-state
  update scene-ledger
  stop

pre_revision:
  snapshot current draft
  identify revision target and allowed scope

post_revision:
  compare before/after
  extract edit-learning candidates
  stop

on_human_edit:
  diff changed files
  classify edit lessons
  ask before promoting lessons into POETICS

on_orientation:
  summarize project state
  identify pending decisions
  stop
```

The stop remains crucial. The model should not snowball from draft to critique to revision unless explicitly asked.

## Roadmap

### Phase 1: Strengthen The Markdown Harness

Goal: improve capability without building a CLI yet.

Actions:

- Revise `narracode.md` to add new structural files.
- Add the scene-cycle as the central loop.
- Add `context/next-scene-pack.md`.
- Add Reader Simulation Agent.
- Add Revision Agents.
- Add check protocols.
- Update `POETICS.md` schema.

Decision point:

- Does this make the current manual workflow noticeably better, or does it become too bureaucratic?

### Phase 2: Add Command Templates

Goal: make workflows repeatable.

Actions:

- Create command markdown templates in `.claude/commands/` or a future `commands/` folder.
- Start with `/orient`, `/context-pack`, `/scene`, `/critique`, `/revise-lines`, `/snapshot`.
- Each command should name exact read/write surfaces.

Decision point:

- Which commands are genuinely used by the human during actual writing?

### Phase 3: Add Deterministic Helpers

Goal: move fragile operations out of prose instructions.

Candidate helpers:

- word count and scene ledger updater
- draft ordering detector
- diff extractor for human edits
- context-pack assembler
- link checker for story exports
- static continuity query over structural files

Decision point:

- Which parts should stay poetic and model-mediated, and which should become deterministic scripts?

### Phase 4: Build A Real CLI Harness

Goal: make Narracode genuinely analogous to Claude Code.

Candidate commands:

```bash
narracode init "premise"
narracode orient
narracode scene
narracode critique drafts/3-arrival.md
narracode revise-lines drafts/3-arrival.md
narracode snapshot
narracode export
```

The CLI should not write prose itself. It should orchestrate files, build context packs, call the model, run checks, and preserve state.

Decision point:

- Should the first real implementation be a local CLI, a Claude Code skill/plugin, or both?

### Phase 5: Build A Literary Evaluation Corpus

Goal: test whether Narracode improves actual writing over time.

Create a small set of internal experiments:

- Same premise, single-shot model.
- Same premise, current Narracode.
- Same premise, expanded Narracode with context pack and checks.
- Same premise, expanded Narracode plus human edit learning.

Evaluate qualitatively:

- Does the story accumulate?
- Does it avoid generic competence?
- Does it remember what matters?
- Does it revise well?
- Does it sustain a style without parodying it?
- Does it preserve ambiguity without becoming incoherent?

## Highest-Value First Changes

If implementing only five things, do these:

1. Add `obligations.md`, `motifs.md`, `reader-state.md`, and `scene-ledger.md`.
2. Add a `pre_scene` context-pack step.
3. Add post-scene literary checks.
4. Add a Reader Simulation Agent.
5. Add a Line Revision Agent and Silence Agent.

These target the biggest gap between short-pass generation and full literary storytelling: accumulated meaning.

## Risks

- Over-structuring can deaden the prose. The harness must preserve uncertainty, silence, and surprise.
- Too many files can make writing feel clerical. Every new state file must earn its keep.
- Checks can become genre policing. They should identify effects, not enforce conventional plot.
- The model may over-learn from human edits. Human approval is required before style lessons become law.
- Context packs can become summaries that flatten the work. They must preserve live pressures, not just facts.

## Guiding Sentence

Narracode should become a system for preserving and intensifying accumulated literary pressure across time.

It should not merely continue stories. It should remember what the story has taught the reader to feel, expect, resist, and notice, then draft from inside that pressure.
